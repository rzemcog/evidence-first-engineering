# Реестр готовых решений для проверки переиспользования

> **Статус:** первичный список кандидатов, НЕ итоговое исследование, НЕ архитектурная рекомендация и НЕ текст будущего гайда. Сформирован для проверки опасения, что проект преждевременно воспроизводит уже существующие решения. Дата первого прохода: 2026-11-12.

## Как оценивать кандидата

Для каждого механизма из D-001–D-013 исследовать готовые продукты/стандарты **параллельно с развитием требований**: **полное соответствие → переиспользовать; частичное → адаптировать или комбинировать; существенный проверенный пробел → исследовать собственную реализацию**. Фактическое соответствие подтверждать документацией, кодом, практическими тестами на репрезентативных задачах и фиксацией неподдерживаемых свойств.

Особое внимание: **ни один пункт в таблице не означает, что продукт уже реализует наши согласованные инварианты целиком** (например, отдельное утверждение версии draft, строгий запрет самоприёмки, доказательство независимости оракула, контроль достаточности усилий).

## Предварительные наблюдения

1. Процедуры **документирования требований и изменений** уже есть в GRACE 4, Spec Kit, OpenSpec, Kiro и Doorstop. Нельзя обосновывать новый реестр только тем, что нужен draft или ID.
2. **Нормативная приёмка конкретной версии draft**, защита от ошибочной интерпретации original intent и проверка конфликтов при параллельных решениях — пока **не подтверждено** как полностью готовая композиция в рассмотренных инструментах; отсутствие подтверждения не равно доказанному пробелу.
3. **Доказательство корректности** имеет разные уровни: BDD-сценарий, assurance case, формально верифицированная теорема. Их нельзя считать взаимозаменяемыми; проверять границы доверия.
4. Главный вопрос может заключаться не в разработке очередного agent harness, а в **совместимости контрактов, проверок и права утверждения** поверх существующих инструментов. Это гипотеза, подлежащая сравнению с альтернативами.

## Следующий исследовательский этап

- Расширять **карту существующих механизмов, сильных сторон, ограничений и комбинаций**, сверяя документацию и код; матрицу соответствия нашим требованиям использовать как вспомогательный инструмент.
- Исследовать стоимость внедрения, интеграции и сопровождения на основе доступных сведений. **Точечные технические испытания** проводить только для существенных вопросов, оставшихся открытыми после анализа источников, или совместимости компонентов.
- **Не выполнять обязательную программу многократных прогонов агентов:** поведенческие T01–T07 сняты с плана D-014.
- На каждом этапе двунаправленно обновлять каталог вариантов и нашу композицию; предложения об изменении утверждённых требований проходят через draft и отдельное принятие пользователем. **Разработка собственного фреймворка не является заранее установленным этапом.**
