# Управление требованиями: сравнительный срез №1

**Дата:** 2026-11-12  
**Кандидаты:** GRACE 4 (Graph-RAG Anchored Code Engineering), OpenSpec, GitHub Spec Kit, Kiro Specs, Doorstop.  
**Этап проверки:** первоисточники и репозитории; **без локальной установки, тестов и измерения стоимости**.  
**Статус:** исторический первый сравнительный срез, составленный до утверждения D-014. Документальную матрицу сохраняем, но **не используем как единственный критерий оценки**, не требуем T01–T07 для каждого кандидата. Актуальная методика: [анализ источников, кода и инженерных подходов](2026-11-12-research-methodology.md).

## Вопрос

Какие существующие решения обеспечивают или могут быть адаптированы для наших D-008, D-010, D-012 и D-013: прослеживаемость первичных требований; versioned draft; отдельное утверждение пользователем; сохранение действующих редакций; контроль stale-base и конфликтов; проактивный поиск пробелов; связь требований с независимыми свидетельствами?

## Метод

Оценка относится только к **установленным возможностям по источникам**. «Не подтверждено» НЕ означает «отсутствует». Категории:

- **Подтверждено:** найдено явное описание механизма в документации, опубликованной конфигурации или skill; это НЕ доказывает стойкость к злонамеренному агенту.
- **Частично:** есть близкая возможность, но не установлено соблюдение нашего полного правила.
- **Не подтверждено:** в просмотренных материалах нет достаточных сведений.
- **Не исследовано:** ещё не оценено на этом проходе.

## По каждому кандидату

### 1. GRACE 4 — самый широкий evidence-oriented контур в этой пятёрке

**Подтверждено опубликованной реализацией:** `grace-init` создаёт `.grace/context/requirements.xml`; `grace-spec` поддерживает нормативные `GraceChangeSpec` со статусами draft/approved, утверждение пользователем и архивы; `grace-plan` отказывается от переписывания уже утверждённого плана, создаёт baseline/target assertions и командные gates; CLI валидирует их. GRACE не только описывает требования, но и связывает их с планом, графом модулей и проверочными свидетельствами.

**Граница:** публичный `requirements.xml.template` содержит `Goals`, `Users`, `Constraints`, но не доказывает наличие отдельного реестра каждой первичной пользовательской реплики с provenance и versioned draft. См. [GRACE deep dive](2026-11-12-grace-requirements.md).

**Источники:**
- [README](https://github.com/osovv/grace-marketplace/blob/main/README.md)
- [grace-spec/SKILL.md](https://github.com/osovv/grace-marketplace/blob/main/skills/grace/grace-spec/SKILL.md)
- [grace-plan/SKILL.md](https://github.com/osovv/grace-marketplace/blob/main/skills/grace/grace-plan/SKILL.md)

### 2. OpenSpec — proposal/delta/archive и редактирование артефактов

**Подтверждено:** `explore → propose → review → apply → archive`; создаются proposal, delta specs, design, tasks; архив хранит delta, а актуальные specs обновляются. `openspec-update-change` по документации спрашивает подтверждение каждой правки артефакта.

**Граница:** описанные действия агента и workflow пока не доказали жёсткую внешнюю авторизацию принятия конкретной versioned draft или изоляцию исполнения от незавершённого согласования. Sync/архивирование и изменение spec не следует автоматически считать нашей политикой «изменять только после одобрения конкретной версии».

**Источники:** [Quickstart](https://openspec.dev/docs/quickstart) · [Skills](https://openspec.dev/docs/skills) · [CLI](https://openspec.dev/docs/cli).

### 3. GitHub Spec Kit — несколько моделей сохранения спецификаций

**Подтверждено:** `specify`, `clarify`, `checklist`, `plan`, `tasks`, `analyze`, `implement`, `converge`; отдельная документация различает flow-back, flow-forward, living spec и constitution-only, не навязывая один способ сохранения после релиза. `converge` проверяет реализацию относительно действующей спецификации и добавляет оставшиеся задачи.

**Граница:** существование `converge` не доказывает соблюдение нашего более строгого `DONE` с независимыми инструментальными свидетельствами. Нет проверенного нами слоя RFC/provenance первичных пользовательских сообщений.

**Источники:** [Quickstart](https://github.github.com/spec-kit/quickstart.html) · [Evolving specs](https://github.github.com/spec-kit/how-to/evolving-specs.html) · [Persisting specs](https://github.github.com/spec-kit/how-to/persisting-specs.html).

### 4. Kiro Specs — требования и проектирование в обоих направлениях

**Подтверждено:** Requirements-First и Design-First; `requirements.md / design.md / tasks.md`; EARS-формулировки; Analyze Requirements для обнаружения противоречий и пробелов; обычные review gates. Quick Spec может пропускать промежуточные review gates, а смена workflow внутри одного Feature Spec, согласно документации, требует создать другой spec.

**Граница:** автоматическое утверждение действующих нормативных требований по отдельной версии draft не проверено; при нашей политике Quick Spec без дополнительных ограничений потенциально нежелателен для изменения утверждённых требований.

**Источники:** [Feature Specs](https://kiro.dev/docs/specs/feature-specs/) · [Best practices](https://kiro.dev/docs/specs/best-practices/) · [Specs overview](https://kiro.dev/docs/specs/).

### 5. Doorstop — реестр и трассировка с review fingerprints

**Подтверждено:** отдельные requirements/test-items в YAML, Git-хранение, уникальные идентификаторы, link validation, `doorstop review`, suspect links. Наблюдение Eclipse Trustable Software Framework описывает `reviewed` checksum, который устаревает при изменении содержимого, и необходимость перепроверки связей.

**Граница:** fingerprint говорит, что содержимое было помечено reviewed, но сам по себе не доказывает семантическую корректность, личность утверждавшего или строгое правило утверждения пользователем конкретного draft. Не содержит штатного agentic analysis и формальных proofs.

**Источники:** [Doorstop docs](https://doorstop.readthedocs.io/en/latest/index.html) · [Quickstart](https://doorstop.readthedocs.io/en/stable/getting-started/quickstart.html) · [Eclipse TSF use](https://gitlab.eclipse.org/eclipse/tsf/tsf/-/blob/v2025.04.30/docs/trudag/using-doorstop.md).

## Выводы первого прохода

1. **GRACE обязательно включать** в сравнение систем управления требованиями. Данные из skills дают прямое подтверждение draft/approved/change bundle и планирования с evidence gates.
2. **Ни один кандидат ещё не подтвердил весь наш контракт** `draft versions + restore + separate approval of exact revision + stale-base conflict + preserved user-intent provenance + independent DONE` только на основании изученных документов.
3. **Не путать отсутствие найденной функции с доказанным отсутствием**. Некоторые функции можно получить из Git, CI или policy слоя без нового специализированного движка.
4. Наиболее перспективная для **экспериментальной проверки**, пока не архитектурная рекомендация, композиция: change proposal workflow (OpenSpec **или** GRACE) + versioned requirements/traceability (Doorstop **или** Git) + внешний контроль приёмки и проверки. Spec Kit/Kiro представляют альтернативные входные workflows, а не обязательные дополнительные слои.
5. GRACE уже включает evidence/graph-контур; добавлять поверх него отдельную параллельную систему требований без проверки необходимости может создать дублированные источники истины.

## Обнаруженные новые вопросы / кандидатные draft

Это **вопросы для обсуждения**, не новые обязательные требования:

- **R-PROP-01:** Нужно ли различать ревью содержимого, фиксацию конкретных байтов/версии и подтверждение прав личности, выдавшей approval? Достаточен ли Git-подписанный commit или требуется отдельный gate?
- **R-PROP-02:** Что считать authoritative source при расхождении реестра первичных требований и живой spec после реализации?
- **R-PROP-03:** Требуется ли защита от конфликтов между *разными* изменениями одного требования, а не только от редактирования одного draft?
- **R-PROP-04:** Какой минимум машинных наблюдений может обосновать отдельное `DONE`, если agentic review говорит «всё готово», а наблюдаемый продукт расходится с критериями?
- **R-PROP-05:** Как предотвратить дублирование нормативных источников между GRACE, OpenSpec, Git и Doorstop при комбинировании?
