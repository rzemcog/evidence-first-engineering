# idea-generator-2: эволюционный поиск идей как компонент EBT-first

**Дата исследования:** 2026-11-22. **Статус:** технический разбор исходного кода, не результаты выполнения и не утверждение нового требования.  
**Первичный источник:** [fltman/idea-generator-2](https://github.com/fltman/idea-generator-2), просмотренный main at [f3f29b443db6e1db916af03c7b49942cacd681d8](https://github.com/fltman/idea-generator-2/commit/f3f29b443db6e1db916af03c7b49942cacd681d8). Лицензия MIT.

## Назначение

Локальное приложение для эволюционного brainstorming: у каждой доски есть goal, пользователь задаёт seed идеи или загружает внешнюю находку, LLM генерирует варианты и комбинации, LLM-judge выставляет оценки и объясняет их, autopilot выбирает следующую операцию, а перспективные идеи могут превращаться в Claude Code project briefs. **Не система верификации ПО и не реестр утверждённых требований.**

## Ограничения, важные для EBT-first

1. **Селекция по субъективной шкале:** оригинальность, реализуемость и impact задаёт та же генеративная среда. Calibrate-скрипт сравнивает 6 заведомо слабых и 5 сильных идей по два раза: это проверка грубой дискриминации шкалы, **не измерение качества инженерных решений** и не валидированное ground truth.
2. **Сближение идей и reward loop:** турнирный отбор усиливает семейства с высокими оценками. Только последние **40 заголовков** предотвращают повторы в промптах; нет доказанной семантической дедупликации, измерения действительно новой полезной информации или остановки по убыванию отдачи. См. [issue #6](https://github.com/fltman/idea-generator-2/issues/6).
3. **Jury оценивает отдельный pitch:** не получает в явном виде полный маршрут гипотез, предыдущие возражения, исходные инженерные ограничения и опубликованные подтверждения/опровержения. Это недостаточно для строгого решения о пригодности технологии.
4. **Отсутствует нормативная граница EBT:** высокая оценка идеи может создать проектный brief, но не является утверждением пользователя, свидетельством выполнения требования или подтверждением correctness.
5. **Безопасность локального API:** [открытый issue #4](https://github.com/fltman/idea-generator-2/issues/4) описывает DNS rebinding и CSRF; [server/app.ts](https://github.com/fltman/idea-generator-2/blob/main/server/app.ts) на просмотренном коммите не проверяет Host/Origin, и есть изменяемый `PUT /api/runtime-settings` с provider baseUrls. **Не подставлять реальные дорогие API keys до hardening; localhost не равно защищённая авторизация.** Это кодовый риск/открытая уязвимость, а не свидетельство фактической эксплуатации.
6. **Бюджет не полноценная гарантия расходов:** некоторые провайдеры не отдают стоимость, а проверка лимитов выполняется до шага и не доказывает hard cap стоимости каждого текущего вызова.
7. **Кросс-платформенность:** `server/engine.ts` для reveal по умолчанию вызывает `execFile('open', ...)`, что предполагает macOS; на Windows этот action нуждается в адаптации. Основной сервер может работать независимо от reveal.

## Предлагаемая роль в универсальной методологии

**Возможный модуль discovery/divergence, не обязательный компонент.** Он может генерировать и визуализировать конкурирующие гипотезы в фазе исследования альтернатив. Граница должна быть строгой:

`hypothesis/idea` → исследование существующих решений и ограничений → объективные источники / сравнительный анализ → `draft proposal` → **отдельное принятие пользователем** (D-010).

Не превращать золотую медаль автоматически в утверждённое требование или архитектурное решение. Отбирать решения по применимым критериям, проверяемым предпосылкам, ограничениям и свойствам, а не только по оценке LLM-judge.

## Кандидаты на идеи для нашей композиции (НЕ согласованные требования)

- **Lineage-aware exploration:** вести граф происхождения исследуемых архитектурных гипотез и их комбинаций, независимо от способа хранения требований.
- **Novelty vs. fitness:** разделить разнообразие механизмов, реализуемость и наличие внешних свидетельств, не штрафуя автоматически нетипичные идеи.
- **Evidence-aware critique:** привязывать к идеям обоснования, возражения и первоисточники. Применять проверку prior art до повышенного ранжирования.
- **Stop on diminishing returns:** учитывать полезность дальнейшей генерации, а не только частоту/бюджет.
- **Approval boundary:** экспорт идеи в development brief — явно **предложение**, не нормативное требование и не разрешение реализации.

## Вердикт

**Стоит изучать как поставщик идей/паттернов эволюционного поиска**, но не выбирать как ядро EBT-first и не интегрировать без реального запроса на отдельный idea-board и проверки безопасности. Лучший немедленно переиспользуемый элемент — генеалогия идей + cross-pollination между исследовательскими направлениями. Для практической работы полезно сравнить это с лёгким графом альтернатив в документах Git прежде чем поднимать отдельный веб-сервис.

**Источник анализировался по коду и документации. Установка, живые вызовы LLM, статистические эксперименты с агентами не выполнялись**, в соответствии с D-014.
